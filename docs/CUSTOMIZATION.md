# Customizing SpecKit PowerPack

PowerPack is designed so that **projects customize configuration and project policy, not the packaged workflow logic**. The project-specific layer should complement PowerPack rather than clone or fork its skills.

The general rule is:

```text
PowerPack invariant
      +
project configuration
      +
project policy/domain skill
      =
effective behavior
```

Project customization may become stricter or add domain-specific validation, but it should not weaken hard safety/convergence invariants such as same-SPEC prerequisites, mandatory review findings, deep-review evidence, capability-driven gates or technical-debt creation rules.

## Configuration layers

After installation, project-local PowerPack configuration lives under:

```text
.specify/powerpack/
├── bin/
│   ├── powerpack.py
│   ├── capabilities.py
│   └── review_protocol.py
├── model-routing.json
├── prerequisites.json
├── quality-gates.json
├── review.json
├── full-cycle.json
├── technical-debt.json
├── deep-review-protocol.md
└── technical-debt-policy.md
```

The package source for those files is under `src/speckit_powerpack/assets/`.

## What should be customized where

| Concern | Project-local customization | Package source | Safe to change? |
|---|---|---|---|
| active agent integration/model routing | `.specify/powerpack/model-routing.json` | `assets/config/default-model-routing.json` | yes |
| same-SPEC prerequisite graph | `.specify/powerpack/prerequisites.json` | generated by `cli.py` | yes, but do not disable prerequisites merely to bypass workflow state |
| build/quality gate | `.specify/powerpack/quality-gates.json` | generated by `cli.py` | yes; prefer `custom_command` for unsupported/ambiguous architectures |
| review mode/provider/Web gate | `.specify/powerpack/review.json` | `assets/config/default-review.json` | yes |
| deep review methodology | `.specify/powerpack/deep-review-protocol.md` | `assets/review/deep-review-protocol.md` | extend/project-specialize; do not weaken approval evidence |
| full-cycle phase policy | `.specify/powerpack/full-cycle.json` | `assets/config/default-full-cycle.json` | yes |
| debt storage/project policies | `.specify/powerpack/technical-debt.json` | `assets/config/default-technical-debt.json` | yes |
| debt safety floor | `.specify/powerpack/technical-debt-policy.md` | `assets/policies/technical-debt.md` | project may add stricter policy but must not weaken floor |
| browser identities/project bindings | global PowerPack config, platform-scoped | `src/speckit_powerpack/cli.py` | use CLI commands rather than editing profile contents |

## Skill-by-skill customization

### `speckit-implement`

**Purpose:** wrap official Spec Kit implementation and record a precise same-SPEC implementation receipt/delta.

Package command:

`src/speckit_powerpack/assets/presets/powerpack-core/commands/speckit.implement.md`

Runtime state implementation:

`src/speckit_powerpack/assets/runtime/powerpack_runtime.py`

Installed runtime:

`.specify/powerpack/bin/powerpack.py`

Customize through project instructions, tasks and the official Spec Kit implementation artifacts. Do not replace delta accounting with language-specific rules. A project should not customize which files count by technology; the runtime compares actual workspace content.

### `speckit-checklist-converge`

**Purpose:** converge requirements/checklist quality only after the same-SPEC checklist step actually ran.

Package command:

`assets/presets/powerpack-core/commands/speckit.checklist-converge.md`

Prerequisite customization:

`.specify/powerpack/prerequisites.json`

Project-specific checklist content belongs in the project checklists/templates/policies. The same-SPEC predecessor rule is a PowerPack invariant and should not be weakened.

### `speckit-converge`

**Purpose:** reconcile implementation against SPEC/plan/tasks and produce remaining specified work.

Package command:

`assets/presets/powerpack-core/commands/speckit.converge.md`

Project-specific cross-layer or domain closure checks should be added as project policy/gates rather than hard-coded into the generic PowerPack command. A Spring-backend-to-React-screen traceability rule, for example, belongs in the project; a generic closure contract can call it.

Active convergence gaps are not technical debt candidates merely because the team wants to finish the cycle.

### `speckit-implement-review`

**Purpose:** independent technical review after implementation convergence.

Canonical package command:

`assets/presets/powerpack-core/commands/speckit.implement-review.md`

There is intentionally only **one** canonical asset. `speckit.implement-review-v2.md` was a transitional migration artifact and must not exist.

Key customization points:

- `.specify/powerpack/review.json` — mode, Codex profile, optional Web gate;
- `.specify/powerpack/model-routing.json` — executor/integration routing defaults;
- `.specify/powerpack/quality-gates.json` — executable validation strategy override;
- `.specify/powerpack/deep-review-protocol.md` — additional project review fronts/probes;
- project constitution/AGENTS/policies — domain invariants the reviewer must enforce.

Hard invariants that must not be weakened:

- Claude executor uses one external Codex review; Codex executor reviews in the current Codex session with no recursive Codex spawn;
- every review round is tied to an immutable head/snapshot;
- previous findings are explicitly revalidated;
- each new round re-reviews the full snapshot, not only the correction delta;
- final adversarial verdict challenge is mandatory;
- every changed file is accounted for in coverage;
- `APPROVED` requires the evidence validator to pass;
- every finding is current-flow work and cannot be moved to debt/backlog to force convergence.

To add project-specific review probes, append fronts/checks to project instructions or a stricter local protocol. Examples: financial idempotency rules, event-order guarantees, APEX metadata invariants, data-retention constraints. Keep generic provider/executor behavior in PowerPack.

### ChatGPT Web gate

Web settings are in `.specify/powerpack/review.json`, while persistent browser identities and project aliases live in the global PowerPack configuration.

Profiles are **platform-scoped**:

```text
browser-profiles/
├── windows/<profile>/
├── linux/<profile>/
└── macos/<profile>/
```

Therefore a profile called `work` on Windows is not the same persistent browser profile as `work` in WSL/Linux or macOS. This prevents accidental authentication/session sharing across OS boundaries.

Use:

```bash
speckit-powerpack review auth login work
speckit-powerpack review project bind my-project https://chatgpt.com/g/g-p-.../project --profile work
speckit-powerpack review project use my-project
speckit-powerpack review project list --all-platforms
```

Bind each platform separately when its authentication or ChatGPT Project access differs.

### `speckit-full-cycle`

**Purpose:** orchestrate existing Spec Kit/PowerPack primitives for one SPEC; it does not reimplement them.

Package command:

`assets/presets/powerpack-core/commands/speckit.full-cycle.md`

Project configuration:

`.specify/powerpack/full-cycle.json`

Default source:

`assets/config/default-full-cycle.json`

Customizable settings include interactive/auto mode, enabled phases and convergence/review round limits. The project can disable optional phases, but should not use configuration to bypass a blocking inconsistency or unresolved finding.

Typical project customization:

```json
{
  "schema_version": 1,
  "mode": "auto",
  "phases": {
    "clarify": true,
    "plan": true,
    "checklist": "when-applicable",
    "checklist_converge": true,
    "tasks": true,
    "analyze": true,
    "implement": true,
    "converge": true,
    "implement_review": true
  },
  "limits": {
    "max_convergence_rounds": 8,
    "max_review_rounds": 5
  }
}
```

Project-specific closure gates can run between convergence and implementation review when the project defines them, but they should be read-only/evidence-oriented and should not hard-code themselves into PowerPack core.

### Technical debt skills

Commands:

- `speckit-debt-create`
- `speckit-debt-list`
- `speckit-debt-consult`
- `speckit-debt-start`
- `speckit-debt-close`

Package source:

`assets/presets/powerpack-core/commands/speckit.debt-*.md`

Project configuration:

`.specify/powerpack/technical-debt.json`

Installed safety floor:

`.specify/powerpack/technical-debt-policy.md`

Projects with an existing governance document should list it in `project_policy_paths`, for example:

```json
{
  "schema_version": 1,
  "backlog_path": "docs/architecture/technical-debt-backlog.md",
  "id_prefix": "MYAPP-TD",
  "project_policy_paths": [
    "docs/architecture/technical-debt-governance.md"
  ]
}
```

The effective policy is the intersection of PowerPack's safety floor and all stricter project rules. Project-specific concepts such as domain owners, prefixes, direction of dependencies or special readiness fields remain local.

A project policy cannot make these items deferrable:

- unresolved implementation-review findings;
- active convergence gaps;
- P0/BLOCKER work;
- work required by current SPEC/acceptance criteria/constitution/mandatory gates.

### `powerpack doctor`

The CLI implementation is `src/speckit_powerpack/cli.py` and the agent command is under the `powerpack-tools` extension.

Projects normally should not modify `doctor`. Extend project diagnostics with project-local commands/skills. Change PowerPack doctor only when the PowerPack installation contract itself changes.

## When to create a project-local skill instead of changing PowerPack

Create a local skill when the rule is about a domain, product architecture or environment policy that is not universally true.

Good project-local examples:

- WASAPI/MMDevice audio lifecycle;
- trading risk/reconciliation invariants;
- Oracle APEX metadata migration constraints;
- endpoint-to-screen traceability for a particular backend/frontend layout;
- WSL-first development policy;
- a proprietary contract versioning scheme.

Prefer changing PowerPack when the behavior is broadly reusable across unrelated projects:

- same-SPEC state receipts;
- review evidence/coverage contracts;
- technical-debt lifecycle semantics;
- full-cycle orchestration;
- capability-driven quality gates;
- platform-scoped browser identity;
- provider/executor routing.

## Upgrade rule

Do not hand-edit generated/materialized `.claude/skills/*` or `.agents/skills/*` as the durable source of PowerPack customization. Change project config/policy or the PowerPack preset/extension source, then reinstall/rematerialize through Spec Kit.
